# Plan: Session Plan Monitoring

- **Spec:** [`spec.md`](spec.md)
- **Status:** Implemented

> **Plan contract:** this is the implementation strategy. It may change as the
> implementation reveals facts; material changes are recorded below.

## Approach

Persist one normalized, bounded latest-plan snapshot per execution-state
session. The stream processor accepts it only after server-side validation and
ordered upsert, then projects one native Plan surface for Research from the
accepted snapshot. The existing Mission Control selected-session token-detail
response adds that snapshot as an optional field. Durable autonomy items remain
untouched and their display is renamed Decision threads.

## Constraints

- Follow [`spec.md`](spec.md) and the additive
  [`Mission Control contract`](../../../contracts/openapi/mission-control.yaml).
- Reuse the execution-state database and existing selected-session Mission
  Control token-detail route; do not create a plan polling endpoint or a new
  service layer.
- Preserve historical sessions and existing clients: plan data is optional and
  legacy rows have no snapshot.
- Treat the plan as untrusted model output: perform a borrowed bounded preflight
  before cloning or typed deserialization, then deserialize it through one strict
  server-side DTO before any database operation, reject unknown step fields, and
  use parameterized SQL only.

## Construction tests

**Integration tests:** accepted stream plan updates persist a normalized latest
snapshot and the existing selected-session Mission Control token-detail response
serializes it according to the OpenAPI contract.

**Manual verification:** run a Research session that calls `update_plan`, open
Mission Control, select that running session, and confirm it shows Current plan
after the normal refresh. Confirm Research shows only Plan and Decision threads
remains unchanged unless an explicit autonomy item exists.

## Design (LLD)

### Design decisions

`session_plans` owns the current operational plan snapshot, keyed by session;
the latest valid update accepted by the server wins. The execution-state
database represents that order with a durable per-session sequence. It is not a
generic event archive, a semantic memory record, or an autonomy item. This
satisfies AC 1–5.

Tempted to store the snapshot in session metadata; declining — a typed table
avoids unsafe read-modify-write merges with unrelated metadata.

Tempted to create an autonomy item for every incomplete step; declining — plan
progress and an explicitly durable decision/follow-up have different lifecycles.

Tempted to add a per-session plan endpoint; declining — the existing
selected-session token-detail response already loads when the user selects a
session and keeps this data scoped to that session.

### Data & schema

Add a migration-owned `session_plans` table with one row per session:

- `session_id TEXT PRIMARY KEY REFERENCES sessions(id) ON DELETE CASCADE`;
- `execution_id TEXT NOT NULL REFERENCES agent_executions(id) ON DELETE CASCADE`;
- normalized plan JSON, optional explanation, `source_event_timestamp`,
  `source_event_sequence`, and server-generated `updated_at`.

The migration also creates `session_plan_counters`, with `session_id TEXT
PRIMARY KEY REFERENCES sessions(id) ON DELETE CASCADE` and
`last_issued_sequence INTEGER NOT NULL`. Existing databases receive empty
tables; the first accepted plan lazily creates its counter at sequence 1. The
counter and snapshot cascade with the session.

Before any database operation, the repository deserializes the model-owned
fields to a strict `SessionPlanInput` DTO: an array of 1–20 steps, with exactly
`step` and `status` on each entry; status is one of `pending`, `in_progress`,
`completed`, or `failed`; each non-empty step is at most 512 UTF-8 bytes; the
optional explanation is at most 1,000 UTF-8 bytes; and the serialized
model-owned JSON is at most 16 KiB. The repository also verifies that the
trusted `execution_id` belongs to the trusted `session_id` before upsert.

`session_id` and `execution_id` come only from `StreamContext`; `updated_at` is
generated by the persistence layer; and the model never supplies an ordering
field. After strict validation and ownership verification, one database
transaction allocates `source_event_sequence` by atomically incrementing that
session's durable counter and writes the snapshot using prepared statements.
The accepted transaction is the ordering point: concurrent root/subagent
updates are linearized there, and the later accepted update is current. The
observational `StreamEvent::timestamp()` is never used to decide which plan
wins, so equal timestamps and wall-clock regression cannot lose a valid update.
The counter update and plan write commit or roll back together; after a daemon
restart, the next allocation resumes at the persisted maximum plus one. The
upsert predicate still requires an incoming sequence strictly greater than the
stored sequence as a defensive invariant. Tests cover concurrent allocation,
equal timestamps, clock regression, lower-sequence rejection at the repository
boundary, and restart/recovery. This satisfies AC 1–3 and 6.

### Interfaces & contracts

`GET /api/executions/v2/mission-control/sessions/:id/tokens` gains optional
`current_plan`; no route is added. It reuses the existing selected-session
lookup and does not disclose plans for unrelated sessions in the 200-row list.
The new OpenAPI document defines the selected-session detail and plan schemas
with a backward pointer to this spec. This satisfies AC 2 and 6.

### Component / module decomposition

`SessionDetailPane` owns the selected session's Current plan presentation so it
uses the existing Mission Control selection. `OpenLoopsPanel` is renamed to
Decision Threads in the UI and tests, but remains backed only by the existing
autonomy transport. `A2uiSurfaceRenderer` retains its native Plan renderer and
no longer receives a projected OpenLoops component. This satisfies AC 3–5.

### State & control flow

`ActionPlanUpdate` → derive trusted context and validate strict model fields →
one transactionally sequenced, parameterized upsert of `session_plans` → on
accepted result,
publish the ordinary `PlanUpdate` and one Plan surface built from that normalized
snapshot → selected `SessionDetailPane` loads `current_plan` through its
existing token-detail request. The ordinary raw gateway event reaches the user
only after an accepted plan update; rejected or persistence-failed updates are
not cloned into a gateway event and publish no Plan surface. Accepted events
receive one persistence attempt with no automatic retry. Diagnostics contain only a bounded reason code, trusted
session/execution identifiers, accepted event sequence, and step count—never
plan text, explanation, or raw JSON. This satisfies AC 1–4.

### Failure, edge cases & resilience

Invalid or oversized model-provided plan payloads are not persisted and do not
replace a valid prior snapshot. A rejected, stale, or persistence-failed update
does not create/update a Plan surface. Foreign-key cascade deletes the snapshot
with its session. Absent rows return `None`; UI renders its empty state. No plan
data is read from or written to the autonomy store. This satisfies AC 1–5.

### Quality attributes (NFRs)

The selected-session response adds at most one 16 KiB snapshot and stores one
capped snapshot per session. The 200-session summary does not include plan
content. UI uses semantic headings and status text, with no agent-supplied HTML
or code rendering. This satisfies AC 3 and 6.

## Tasks

### T1: Persist a bounded current plan per session

**Depends on:** none

**Touches:** `services/execution-state/src/{types,repository,service}.rs`, `stores/zbot-runtime-sqlite/src/schema.rs`

**Tests:**
- TDD: a valid snapshot is stored and the later server-accepted per-session
  sequence replaces it (AC 1).
- TDD: malformed, unknown-field, SQL-shaped, oversized, overlong, stale, and
  cross-execution plan data are rejected without destroying the prior valid
  snapshot (AC 1).
- TDD: equal wall-clock timestamps and a simulated clock regression use the
  durable server acceptance sequence; concurrent allocation and a daemon
  restart continue above the persisted sequence, while a lower sequence is
  rejected at the repository boundary (AC 1).
- TDD: deleting a session cascades to its plan; old databases migrate without a
  session plan and remain readable (AC 2).

**Approach:**
- Define strict typed plan-step/input/snapshot records with explicit byte and
  serialized payload limits.
- Add the migration and repository/service operations with ownership validation,
  prepared upsert, durable atomic session-sequence allocation, ordering
  predicate, and selected-session lookup.

**Done when:** repository and migration tests prove validated latest-snapshot
semantics and legacy compatibility.

### T2: Persist updates and publish one Research plan surface

**Depends on:** T1

**Touches:** `gateway/gateway-execution/src/invoke/stream_event_processor.rs`

**Tests:**
- TDD: processing an accepted `ActionPlanUpdate` saves its snapshot before the
  Plan surface is emitted; rejected updates suppress their raw gateway event
  and emit no surface (AC 1).
- TDD: the projected descriptor contains `PlanChecklist` only and points at the
  accepted normalized plan data (AC 4).

**Approach:**
- Convert the structured plan event into the strict server-side input. Persist
  once without retry and log a redacted reason code, never model content, if it
  is rejected or fails.
- Remove the synthetic `OpenLoops` component and duplicate data path.

**Done when:** a plan update produces one Research Plan surface and leaves no
autonomy side effect.

### T3: Project and render Current plan in Mission Control

**Depends on:** T1, T2

**Touches:** `services/execution-state/src/{types,repository}.rs`, `apps/ui/src/features/mission-control/*`, `apps/ui/src/services/transport/{types,http.class.test.ts}`

**Tests:**
- TDD: a selected Mission Control token-detail response includes its current
  plan only when one exists (AC 2, AC 6).
- Visual/component: selecting a planned session renders Current plan steps and
  status; no-plan renders the exact empty-state text (AC 3).
- Visual/component: durable autonomy UI is labelled Decision threads and its
  count ignores the current plan (AC 5).

**Approach:**
- Add the optional typed selected-session field through transport and retain the
  existing selection flow. Do not include plans in the session-list response.
- Expose the existing successful Mission Control list-refresh generation to the
  selected-token hook. While the selected session is running, that hook reloads
  its existing token-detail response once per normal list refresh; no second
  polling loop is introduced.
- Render the plan in the existing detail pane and rename the autonomy panel;
  do not change its storage or transitions.

**Done when:** Monitoring distinguishes a selected session's plan from durable
decision threads in both populated and empty states.

## Rollout

The migration is additive and creates an empty table. Deploy it with the daemon;
older sessions remain usable and gain a plan only after a new `update_plan`.
Rollback leaves the additive table unused by older code.

## Risks

- The plan payload is model-produced; persistence must reject malformed or
  oversized snapshots without disrupting execution.
- Model-owned plan text must never be written to rejection diagnostics.
- Plan reads must remain scoped to the existing selected-session visibility
  lookup and must not expand the session-summary payload.
- Existing unrelated working-tree changes require scoped verification only.
