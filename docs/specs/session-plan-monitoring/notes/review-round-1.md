# Plan review — round 1

**1. Typed pre-persistence validation and SQL-sink rules are incomplete.** `docs/specs/session-plan-monitoring/plan.md:55-61`; `contracts/openapi/mission-control.yaml:28-47`. The contract bounds known fields, but permits unknown properties, while the plan does not define the serialized-byte cap or require typed deserialization and parameterized upsert queries. Fix: define one server-side DTO for `ActionPlanUpdate` with rejected unknown fields, exact status enum, explicit UTF-8 byte/step/count/serialized-JSON limits, and validation before any database operation. Require prepared/parameterized upsert queries only. Test SQL-shaped strings, unknown fields, and oversized JSON preserve the prior snapshot.

**2. Session, execution, time, and replacement order are not specified as server-derived.** `docs/specs/session-plan-monitoring/spec.md:26-31`; `docs/specs/session-plan-monitoring/plan.md:79-85`; `contracts/openapi/mission-control.yaml:36-47`. A model plan must not be able to supply or spoof its owning execution/session or overwrite a newer snapshot through a delayed event. Fix: derive `session_id`, `execution_id`, and `updated_at` exclusively from trusted stream context; persist a server monotonic event sequence/timestamp and conditionally replace only when newer. Keep model input limited to validated explanation and steps. Add delayed/out-of-order and cross-execution tests.

**3. Rejection diagnostics and retry behavior are underspecified.** `docs/specs/session-plan-monitoring/plan.md:81-92`; `docs/specs/session-plan-monitoring/plan.md:134-137`. The plan says failures are logged, but does not prohibit raw model payloads in logs or define a single-attempt/no-retry policy. Model text could leak into diagnostics or cause repeated expensive persistence attempts. Fix: log only redacted reason codes, bounded lengths/counts, and trusted correlation IDs—never steps, explanation, or raw JSON. Validate before persistence; make one persistence attempt per accepted event, with no automatic retry loop. Test invalid/oversized persistence failures leave the prior snapshot untouched and emit no model content.

**4. The 200-session summary lacks a composite payload and visibility budget.** `docs/specs/session-plan-monitoring/plan.md:94-98`; `contracts/openapi/mission-control.yaml:8-25,42-46`. Each plan is bounded, but up to 200 summaries can each contain 50 × 1,000-character steps plus explanation. This is bounded but can still create a large running-session response and broadens disclosure from the selected session to every returned summary. Fix: set a total response-byte/plan-count budget and ensure the batch join uses the existing session-visibility policy before projecting `current_plan`; test the maximum batch remains within the agreed payload budget.

**5. Invalid plans can still create/update a Research Plan surface.** `docs/specs/session-plan-monitoring/plan.md:81`. Validation/upsert precedes projection, but persistence rejection must not prevent the event; the current processor independently publishes from the raw `ActionPlanUpdate`. Fix: make persistence return an accepted normalized snapshot/outcome and publish a Plan surface only from that accepted snapshot. The raw gateway event may still broadcast. Test invalid input leaves the prior snapshot and emits no new/updated Plan surface.

**6. `session_plans` has no enforceable ownership or deletion lifecycle.** `docs/specs/session-plan-monitoring/plan.md:57`. The design promises one row per session but specifies neither a unique/primary key nor cleanup when the owning session is deleted. Fix: require `session_id` as `PRIMARY KEY` with `FOREIGN KEY ... REFERENCES sessions(id) ON DELETE CASCADE` (or explicitly extend every session-delete path); validate that `execution_id` belongs to that session. Add deletion/cascade coverage.

**7. “Latest” is undefined for concurrent or late-arriving plan updates.** `docs/specs/session-plan-monitoring/plan.md:42`; `docs/specs/session-plan-monitoring/plan.md:81`. The design says newest/latest wins without defining the ordering source or atomic conflict rule. Independent root/subagent streams can race. Fix: define server-owned acceptance time or source-event timestamp semantics and an atomic upsert predicate, then test that an older/late update cannot overwrite the chosen latest snapshot.

**8. The new OpenAPI query constraints do not match the existing route behavior.** `contracts/openapi/mission-control.yaml:12`. The contract declares `limit` 1–200, while the repository clamps values above 200 and permits `0` as `LIMIT 0`. Fix: either add handler validation with documented 400 responses, or adjust the contract to describe the existing clamp/zero semantics.
