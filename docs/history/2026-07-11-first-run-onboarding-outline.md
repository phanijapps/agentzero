# Outline — first-run onboarding for non-technical zbot users

## Sub-question 1: What does zbot currently require before a user can send a first message?

**Rationale:** The proposed flow must remove or automate real prerequisites rather than hide them.

## Sub-question 2: Which choices are essential before first chat, and which can be safely deferred?

**Rationale:** A non-technical user should make only decisions that materially affect their first successful outcome.

## Sub-question 3: How should provider, model, API key, and local-model choices be framed?

**Rationale:** These determine cost, privacy, capability, and setup failure modes.

## Sub-question 4: What defaults create a comfortable and safe first experience?

**Rationale:** Defaults should provide useful chat without exposing advanced agent, filesystem, or integration risk prematurely.

## Sub-question 5: How should key validation, error recovery, and privacy disclosures work?

**Rationale:** Credential and connectivity failures are the highest-likelihood first-run blockers.

## Sub-question 6: What installation and first-run flows are supported by current practitioner guidance?

**Rationale:** The setup should use proven progressive-disclosure and recovery patterns rather than a developer-oriented configuration wizard.

## Open / second-order sub-questions

- Which providers and models should be presented in the first release, and in what order?
- Should a local-model path be fully guided or positioned as an advanced option?
- What telemetry, if any, is appropriate before consent?
